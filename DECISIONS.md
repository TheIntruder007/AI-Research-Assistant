## D-001 — Project workspace location and structure
- **Date:** 2026-08-26
- **Decision:** Create the project at `Desktop/AI-Research-Assistant` with the standard `services/ orchestrator/ shared/ outputs/ docs/ tests/ scripts/` layout.
- **Reason:** Matches the required architecture; keeps each pipeline stage independently testable.
- **Alternatives considered:** Monolithic single-app structure — rejected, breaks the "test each service in isolation" requirement.
- **Impact:** All later services/adapters follow this layout.

## D-002 — Local AI model selection: qwen3.5:9b
- **Date:** 2026-08-26
- **Decision:** Use `qwen3.5:9b` (6.6GB) via Ollama as the default local reasoning/generation model.
- **Reason:**
  - Machine hardware: Intel i7-13700HX (16 cores/24 threads), 16GB system RAM, NVIDIA RTX 4060 Laptop GPU with 8GB VRAM (verified via `nvidia-smi`).
  - qwen3.5:9b (6.6GB) fits comfortably within 8GB VRAM with headroom for context.
  - Larger variants (qwen3.5:27b ≈17GB, qwen3.5:35b ≈24GB) exceed available VRAM and would require heavy CPU offload on a 16GB-RAM machine, making development unusably slow.
  - Verified via web search against the live Ollama library (not guessed) that `qwen3.5:9b` is a real, currently published tag.
- **Alternatives considered:** qwen3.5:27b/35b (rejected — hardware too small), a non-Qwen family (rejected — doc specifies Qwen 3.5 family as preferred starting point and it is available and fits).
- **Impact:** All four services call the local model through an `LLMProvider` abstraction defaulting to `qwen3.5:9b`; swapping models later requires no service code changes.
- **Installation command:** `ollama pull qwen3.5:9b`
- **Verification result:** Confirmed working 2026-08-27. `ollama run qwen3.5:9b "Reply with exactly: OK"` responded correctly (model shows a visible reasoning trace before its answer, then replied "OK"). Download took far longer than expected (~24h) due to two compounding environmental issues on this machine, unrelated to the model choice itself — see D-008.

## D-008 — Ollama model storage moved to D: drive
- **Date:** 2026-08-27
- **Decision:** Set `OLLAMA_MODELS=D:\ollama_models` (persisted as a Windows user environment variable) instead of the default `C:\Users\<user>\.ollama\models`.
- **Reason:** The `qwen3.5:9b` pull repeatedly failed/stalled over many hours. Initial diagnosis suspected network throttling by the Killer Wi-Fi adapter's traffic-shaping software (confirmed as a contributing factor — `curl` to the same registry URL was consistently faster than `ollama.exe`'s own download). However, the actual failure was a `curl exit code 23` (disk write failure): the C: drive was completely full (0 bytes free at the time), which silently truncated every download attempt regardless of network speed. This was the root cause; the network throttling only made the symptom slower to diagnose.
- **Alternatives considered:** Freeing up space on C: instead — rejected as fragile; C: was at 98% capacity independent of this project, so any future model pull would risk hitting the same wall. D: has 52GB free, comfortably enough for this and future models.
- **Impact:** The Ollama tray watchdog (`ollama app.exe`, which auto-relaunches `ollama.exe serve` on kill) had to be stopped so a manually-launched server with the correct `OLLAMA_MODELS` env var would stick. `shared/utilities/llm_provider.py` is unaffected (it only needs `OLLAMA_HOST`, not the model storage path). Anyone resuming this project on this machine should launch Ollama's server manually with `OLLAMA_MODELS=D:\ollama_models` if the tray app was disabled, or re-enable the tray app after confirming it picks up the persisted env var on next login.

## D-009 — Reliability fixes for local-model structured output (discovery pipeline)
- **Date:** 2026-08-27
- **Decision:** Four fixes were required to get the Research Discovery Service running reliably end-to-end against `qwen3.5:9b`, all in `shared/utilities/llm_provider.py` and `services/research-discovery/discovery/`:
  1. **`think=False` on all three LLM calls** (query generation, full-text mining, gap/novelty analysis). The model runs a visible "thinking" reasoning mode by default, and reasoning tokens count against the same output budget as the actual JSON answer. Thinking unpredictably consumed the entire token budget before any schema JSON was produced — first on query generation (1000-token budget, empty result), then on full-text mining (12000-token budget, empty result, handled gracefully as best-effort), then on the main gap analysis (32000-token budget, empty result — NOT best-effort, aborted the run). Confirmed via direct Ollama API testing that `think:false` produces the same correct JSON in a fraction of the time and cost.
  2. **Explicit, tiered `num_ctx`** (`_context_window_for()` in `llm_provider.py`). Ollama's server-side default context window is far smaller than this model's 256K support and silently truncates generation once prompt+output exceed it — regardless of `num_predict`/`max_tokens`. A single large fixed context (tried at 24576) fixed the truncation but caused a different problem: on an 8GB GPU, a bigger context reserves proportionally more VRAM for KV cache, and this pushed inference into partial CPU offload (`31/34 layers to GPU`) even for small calls, making everything much slower. The fix scales `num_ctx` to each call's actual need (`_context_window_for`, tiered at 4096/8192/16384/24576/32768) so cheap calls stay cheap and only the calls that need headroom pay for it.
  3. **Trimmed `REPORT_SCHEMA` verbosity and reduced `max_tokens`** in `analysis.py` (themes 3-6→2-4, gaps 4-8→2-4; mining 12000→6000, gap analysis 32000→8000). A schema demanding 4-8 well-evidenced gaps is disproportionate for a 6-9 paper MVP corpus, and was driving unnecessarily long generations on this hardware.
  4. **`MAX_CANDIDATES_FOR_ANALYSIS = 5` cap** in `pipeline.py`. The gap-analysis schema requires one full JSON entry per author-flagged candidate with no cap of its own, so an uncapped mining result (observed: 10 candidates) scaled the final synthesis call's output size directly. Mining already orders candidates most-to-least substantive, so capping keeps the strongest ones.
  - A fifth, trivial bug (not a design decision, just a typo) was also fixed: `analyze_gaps()` read `comp.input_tokens`/`comp.output_tokens`, but `llm_provider.Completion` names those fields `prompt_tokens`/`completion_tokens`. This crashed the pipeline on the very last line, *after* a fully successful generation — first found when a run reached `n_tokens=8235, truncated=0` (proof the earlier fixes worked) and then crashed on this attribute access.
- **Reason:** Verified via multiple full end-to-end runs against the live model; see TILL_NOW.md for the successful run's stats.
- **Alternatives considered:** For (2), raising `max_tokens`/context indefinitely instead of tiering — rejected, this is what caused the CPU-offload slowdown in the first place. For (3)/(4), leaving the schema as-is and just waiting longer — rejected as impractical; a production run needs to complete in reasonable time on this hardware.
- **Impact:** `services/research-discovery/service.py::run_discovery()` now completes reliably end-to-end. This hardware (RTX 4060 8GB) is inherently slow for larger-context calls on a 9B model — later services should budget for this (keep schemas as compact as the task allows, cap any unbounded list before it reaches a synthesis prompt, and prefer `think=False` unless a specific step needs visible reasoning with a tested, generous token budget).

## D-007 — Research Discovery Service adaptation approach
- **Date:** 2026-08-26
- **Decision:** The Research Discovery Service's core pipeline (query generation → multi-source search → dedupe → rank → full-text mining → gap/novelty analysis) is retained as an async-generator pipeline emitting structured progress events — this already matches the project's required progress-event architecture. Adapted:
  - Swapped the cloud-provider LLM layer for `shared/utilities/llm_provider.py` (local Ollama only, no cloud fallback).
  - Removed personal-library integrations (a reference-manager sync feature and a citation-context enrichment feature) — out of scope for the MVP, added complexity/failure surface, and required data this system doesn't have.
  - Removed the bundled web frontend and HTTP server layer — this becomes an in-process importable service (`services/research-discovery/service.py`) called directly by the orchestrator, not a standalone web app.
  - Extended the gap-analysis output schema with explicit `novelty_analysis` (summary, supporting gaps, confidence, caveats) and `confidence_notes` fields, and extended query generation to also produce a `research_interpretation` field — both required by the project's output contract but not present in the original schema.
- **Reason:** Reuse-first per project rules; the four literature sources kept (Semantic Scholar, OpenAlex, PubMed, arXiv) all work with no API key, satisfying the "local AI + no external key" requirement for this stage.
- **Alternatives considered:** Running it as a separate HTTP microservice — rejected for MVP simplicity; can be revisited if a future web frontend needs direct access to this stage in isolation.
- **Impact:** `services/research-discovery/service.py::run_discovery()` is the stable entry point Service 2 and the orchestrator depend on; output conforms to `shared/contracts/discovery_contract.py::DiscoveryResult`.

## D-010 — Research Writing Service adaptation approach
- **Date:** 2026-08-27
- **Decision:** Adapted a LangGraph-based literature-review/writing agent as the Research Writing Service (`services/research-writing/`), reusing its outline-driven section-writing graph (`writing/graph.py`, `writing/modules/*`) and replacing only what didn't fit:
  - Its original two-agent design (search + write) is reduced to the writing agent only — Service 1 already covers search/discovery, so its own literature-search step is dropped entirely.
  - Its evidence-extraction step runs directly on Service 1's already-fetched abstracts rather than requiring the original design's manual PDF-download step. `services/research-writing/writing_prep.py` builds one Markdown "literature file" per selected paper (front matter + abstract, `evidence_depth: abstract`) and a heading outline (one root heading, gap titles as literature-review subsections) directly from a `DiscoveryResult` — no re-scraping.
  - Its LLM call layer was swappable as designed: `writing/adapters/ollama_model.py` implements the repo's `LanguageModel` protocol against `shared/utilities/llm_provider.py` (the same local-first provider from D-003), using Ollama's native schema-constrained decoding rather than the original prompt-engineered JSON-mode adapter (more reliable on a small local model — consistent with D-009's findings).
  - `shared/contracts/writing_contract.py` defines `WritingRequest`/`WritingResult` as the stage's input/output contract; `WritingRequest.target_format` is extensible (`IEEE`/`Springer`/`ACM`/`APA`/`Other` today, mapped to a citation style, with `format_other_name` for anything not yet listed) per the project's format requirement.
  - `services/research-writing/service.py::run_writing()` is the stable async-generator entry point (progress events + final `WritingResult`), matching Service 1's event-streaming shape.
  - Runs with `FAST_REVIEW_CONFIG` (all revision/audit rounds disabled, one retry each for section writing and card extraction) — this hardware is too slow for the graph's default multi-round revise/audit loop (each round re-runs every leaf section through the model).
  - `_context_window_for()` in `shared/utilities/llm_provider.py` (D-009) was extended to take the actual prompt length (`prompt_chars`) rather than sizing purely off `max_tokens` — the writing graph's per-section prompts (full literature files, not just a short query) are large enough that sizing from output length alone under-allocated context and caused slow mid-generation context-window shifts. Discovery's `Paper`/`PaperMetadata` now also carry the raw `abstract` field through to the contract (previously only a `has_abstract` boolean was exposed), since the writing service's literature files need the actual text.
- **Reason:** Reuse-first per project rules (see the "Do Not Rebuild Existing Work" working rule); the graph's outline-driven, evidence-file-based writing approach already matches this project's "evidence-grounded draft, structured contracts, no loose text between services" requirement.
- **Alternatives considered:** Keeping the original two-agent search+write pipeline and running Service 1's output through it as if it were freshly discovered — rejected, redundant work and loses Service 1's gap/novelty analysis. Full-text PDF ingestion instead of abstract-only literature files — deferred; Service 1 doesn't reliably produce full text for every paper, and abstract-depth evidence is sufficient to validate the pipeline wiring end-to-end (a full-text upgrade is a Service 1 enhancement, not a Service 2 blocker).
- **Known limitation:** On this hardware, leaf-section writing reliability (one LLM call per outline leaf, run at `max_concurrency=2`) is the main remaining source of partial/empty sections in a full-size outline — mitigated by capping retries (not eliminating the failure) and reported via `WritingResult.draft_metadata.warnings`/`errors` rather than hidden. A faster model/machine would allow re-enabling revision/audit rounds and higher concurrency.
- **Verification:** Unit tests (`tests/services/test_writing_prep.py`) cover outline/literature-file generation in isolation. `tests/services/test_writing_pipeline_integration.py` runs the full service against the live local model with a minimal two-paper/four-section case and checks for real cited, evidence-grounded output (skips cleanly if Ollama isn't reachable). `scripts/smoke_test_writing.py` is a manual end-to-end runner for the same minimal case. A production-sized outline was not run end-to-end during development — each leaf section is a separate LLM call, so a full run is expected to take a long time on this hardware (see the FAST_REVIEW_CONFIG note above); this is tracked as a follow-up before Review 2, not a blocker for Service 2 working "in isolation."
- **Impact:** `services/research-writing/service.py::run_writing()` is the stable entry point Service 3 depends on; output conforms to `shared/contracts/writing_contract.py::WritingResult`.

## D-011 — Fixed near-total section failure in Service 2's first full-corpus run
- **Date:** 2026-08-27
- **Decision:** Removed per-research-gap literature-review subsections from `writing_prep.py::build_outline()` and instead render Discovery's research gaps and novelty analysis directly as Markdown (`render_research_gap_section()`), spliced into the assembled draft by `service.py` rather than routed through the writing graph's evidence-gated leaf writer.
- **Reason:** A real end-to-end timing run (6 papers, 5 Discovery-identified gaps, ~15.4 minutes total: 245s discovery + 681s writing) produced only 2 of 13 outline sections successfully — all 5 per-gap subsections plus Research Gap, Proposed Novelty, Methodology, and Discussion failed with "insufficient evidence." Root cause, confirmed by inspecting the run's `tag_definitions.json`/`tag_coverage.json`/`literature_cards/*.json`: each Discovery gap is already a narrow, specific statement (e.g. "Absence of Direct Measures of Neuronal Metabolism... in Diabetic Models") derived from ~1 paper. Turning each into its own literature-review subsection made the writing graph's own tag-semantics step (`define_tag_semantics.md`) generate matching narrow `include_when`/`exclude_when` criteria, which then (correctly, per that step's own "never fill a tag by inference" rule) excluded almost the entire rest of the corpus — even a paper squarely on-topic (Anton et al., on IF's metabolic mechanisms) got zero points assigned to *any* tag, including the root/general one, because none of its content matched any gap's narrow criteria. This is the writing graph behaving exactly as designed for a genuine multi-paper thematic review outline; the bug was in how Service 2's outline builder used it.
- **Alternatives considered:** Loosening the tag-semantics prompt to be less strict — rejected, this is the underlying tool's core evidence-integrity guarantee and the project explicitly requires "not silently inventing" unsupported content. Keeping per-gap subsections but feeding full-text instead of abstracts — deferred; wouldn't fix the structural mismatch (a gap statement about one specific missing measurement isn't a topic multiple papers can speak to, regardless of evidence depth). The fix instead treats Discovery's gap/novelty analysis for what it already is: Service 1's own finished synthesis, not raw literature requiring re-evidencing by Service 2.
- **Impact:** `services/research-writing/writing_prep.py::build_outline()` now produces a flat Introduction / Literature Review / Limitations / Conclusion outline; `render_research_gap_section()` and its splice point in `service.py::run_writing()` are new. A related, separate issue was also observed and left unfixed: one of Service 1's 6 selected papers for the first run was an unrelated asthma-management guideline, a Discovery-side relevance/ranking bug worth investigating before Review 2, not a Service 2 defect.
- **Re-verification (same day, second full run, fresh 6-paper corpus):** The guaranteed-failure structural bug is confirmed fixed — no run-wide "insufficient evidence" wipeout. However, still only 2 of 4 leaf sections succeeded, this time for a different, more ordinary reason: `qwen3.5:9b` twice assigned the same evidence point to both a tag and its own ancestor (e.g. `TAG-ROOT` and `TAG-2`), which `build_literature_card.md`'s "assign only to the deepest matching tag" rule and the graph's own validation correctly reject — the affected paper's card failed after its retry budget (`max_card_attempts=2`), starving the Literature Review section of evidence and cascading into an empty-content validation error. This is model instruction-following reliability, not an outline-design defect, and is the same category of hardware/model limitation D-010 already flagged ("leaf-section writing reliability... is the main remaining source of partial/empty sections... mitigated by capping retries, not eliminated"). Not fixing further for now — the cost/benefit of chasing every small-model tagging mistake is poor on this hardware (each attempt is itself a ~15-minute run), and Service 2's contract already surfaces such failures honestly via `warnings`/`errors` rather than silently producing ungrounded content. Revisit if a faster model/machine becomes available (D-010's suggestion to re-enable revision/audit rounds and raise `max_card_attempts` would likely help).

## D-012 — Citation Verification Service adaptation approach
- **Date:** 2026-08-27
- **Decision:** Adapted the DOI/URL-verification piece of a full-stack literature-review web app as the Citation Verification Service (`services/verification/`) — not the whole source app, which is a paid-API-heavy (Scopus, Zotero, SerpAPI, OpenRouter), full-stack (FastAPI + Next.js) research tool built around a different end-to-end workflow than this project's pipeline.
  - Reused only its narrow, genuinely reusable core idea: parse a DOI out of each rendered reference-list entry and check it against a scholarly API, never inventing or silently repairing an unresolvable one. The source app's own DOI check uses paid Scopus with a Crossref fallback; this project has no Scopus key, so Service 3 uses Crossref as primary and OpenAlex as a fallback (both free/keyless — same "no external key" pattern as Service 1, D-007, and OpenAlex is already a dependency this project trusts).
  - `shared/contracts/verification_contract.py` defines `VerificationRequest`/`VerificationResult` as the stage's input/output contract, taking Service 2's `WritingResult` directly (no re-parsing of raw draft text needed — `WritingResult.reference_candidates` already gives one formatted, DOI-bearing string per reference).
  - `services/verification/service.py::run_verification()` is the async-generator entry point (progress events + final `VerificationResult`), matching Services 1–2's event-streaming shape. `extract_doi()` handles both DOI-suffix styles Service 2's citation formatter produces (`doi: 10.x/y` for IEEE/Vancouver, `https://doi.org/10.x/y` for author-year/MLA styles).
  - Three outcomes per reference, never collapsed into a binary pass/fail: `verified` (DOI resolved), `invalid` (a DOI was found but resolves nowhere — flagged as possibly incorrect or fabricated), `unverifiable` (no DOI present to check at all — flagged, not treated as a failure). A basic `missing_references` check compares `draft_metadata.papers_cited` against the reference-list count as a coarse citation-completeness signal.
  - Deliberately does NOT attempt the source app's "re-search for a replacement paper" step for a failed DOI (see its `api/workflow.py` re-search-agent pattern) — out of scope for this MVP; flagging honestly satisfies the "must not silently invent or repair" requirement without adding a second corpus-search dependency. Also deliberately does NOT attempt positional in-text citation-marker verification (matching every `[1]`/`(Author, Year)` occurrence in the draft body back to a reference) — the reference-list-level check (verified/invalid/unverifiable counts plus the cited-vs-listed count check) is the higher-value, lower-complexity check for now; full positional verification is a documented future enhancement, not a blocker.
- **Reason:** Reuse-first per project rules; a full paid-API research app would have been a poor fit to adapt wholesale, but its DOI-verification pattern (grounding citations against a real external source rather than trusting LLM output) is exactly this project's Service 3 requirement, and translates cleanly to a keyless equivalent.
- **Alternatives considered:** Adapting the source app's full retrieval+synthesis+Zotero pipeline — rejected, redundant with Services 1–2 and dependent on paid keys this project doesn't use. Requiring a Scopus key to match the source app's primary check — rejected, breaks the project's local-first/no-external-key requirement for a service this early in the pipeline. Attempting automatic reference repair via re-search — deferred, not required by the MVP spec ("flag it... otherwise keep it as a validation issue" already satisfies the requirement).
- **Verification:** Unit tests (`tests/services/test_verification_service.py`) cover DOI extraction across citation styles and the verified/invalid/unverifiable/missing-references classification logic using a mocked HTTP transport (no network needed). An integration test (`tests/services/test_verification_pipeline_integration.py`) and `scripts/smoke_test_verification.py` both run against the live Crossref/OpenAlex APIs with one real DOI, one fabricated DOI, and one DOI-less reference, confirming all three outcome branches — verified live end-to-end.
- **Impact:** `services/verification/service.py::run_verification()` is the stable entry point Service 4 depends on; output conforms to `shared/contracts/verification_contract.py::VerificationResult`.

## D-013 — Quality Assurance Service adaptation approach
- **Date:** 2026-08-27
- **Decision:** Adapted the deterministic (non-API) citation-audit and evaluation-reflection logic of a larger multi-agent literature-review system as the Quality Assurance Service (`services/quality-assurance/`) — not that system's own discovery/writing/persistence/workbench infrastructure, which duplicates Services 1–3 and is built around a different corpus format.
  - Reused the core idea of its citation auditor: scan the draft for high-risk factual/empirical sentences (numbers, "shows/reports/demonstrates/improves" etc.) with no citation at all (`find_missing_citations`), and separately flag *cited* sentences whose wording doesn't token-overlap enough with the paper(s) they cite (`find_unsupported_claims`) — a lightweight, fully deterministic claim-to-evidence alignment check requiring no extra model call.
  - Adapted, not copied: the source system's citation pattern (`[LetterKey]`) doesn't match this project's numeric `[1]`/`[2]` IEEE-style citations, so `services/quality-assurance/service.py` uses its own `\[(\d+)\]` pattern. Its claim-support check compares against an in-repo `data/papers.json` corpus's title/category/contribution/tags; this project instead matches each numbered reference back to its original `DiscoveryResult` paper **by DOI** (`build_reference_profiles`) and compares against that paper's real title/abstract text — richer and already-verified (via Service 3) rather than a curated in-repo fixture.
  - Deliberately treats an unmatched DOI (no Discovery record found) as a **known limitation**, not a false "unsupported claim" — the source system's design assumes every citation key always resolves to a full corpus profile, which doesn't hold here (Service 3 can verify a DOI exists without Service 4 being able to trace it back to the exact Discovery record, e.g. if metadata normalization differs slightly).
  - `shared/contracts/qa_contract.py` defines `QualityAssuranceRequest`/`QualityAssuranceResult`. Unlike Services 1–3, the request bundles all three prior stages' outputs (`DiscoveryResult`, `WritingResult`, `VerificationResult`) — an independent final audit needs the original evidence, the draft, and the citation checks together, not just the immediately preceding stage's output.
  - `services/quality-assurance/service.py::run_quality_assurance()` is the async-generator entry point, matching Services 1–3's event-streaming shape, even though the work itself is synchronous — kept for pipeline consistency (the orchestrator can treat all four stages uniformly).
  - **Deliberately does not call the local LLM at all.** Grading a draft with the same model that wrote it (`qwen3.5:9b`) is a weaker independence guarantee than deterministic, rule-based checks, and this hardware is already the bottleneck for Services 1–2 (D-009/D-010) — a QA pass that adds more slow model calls would undercut its own point as a fast, final, trustworthy gate. Scores (`citation_integrity`, `claim_source_alignment`, `process_control`, `literature_coverage`, `overall`, each 0–5) are computed from Service 3's verified/invalid/unverifiable counts, Service 4's own missing-citation/unsupported-claim/missing-section findings, and Service 2's own reported warnings/errors — mirroring the source system's non-API deterministic scoring path, not its optional API-backed one.
  - Also adapted, not reused: the source system's `FinalVerificationReviewer` (checks that a separate "polish" pass didn't silently change citations/headings/references). This project's pipeline has no separate polish stage between Writing and Verification, so that check doesn't apply — out of scope, not overlooked.
- **Reason:** Reuse-first per project rules; the source system's citation-integrity and claim-alignment heuristics are genuinely reusable ideas independent of its specific corpus format or API mode, and a deterministic final gate is both faster and more trustworthy than another LLM pass on this hardware.
- **Alternatives considered:** Running the source system's full multi-agent review/revision loop (writer ↔ reviewer ↔ polish iterations) — rejected, duplicates Service 2's own writing loop and this project's Services 1–3 already produce the evidence/citation checks that loop exists to enforce. Using the local LLM for an "independent" review pass — rejected per the self-grading concern above; revisit only if a second, materially different model becomes available on this hardware. Requiring every reference to resolve to a matched Discovery record — rejected, too strict given Service 3 verifies DOIs independently of Service 4's own DOI-to-record matching.
- **Verification:** Unit tests (`tests/services/test_qa_service.py`) cover missing-citation detection, DOI-based profile matching, unsupported-claim detection (including the "don't flag an unmatched DOI" case), missing-section detection, and a full `run_quality_assurance()` pass — all fast and network-free (no LLM, no HTTP). `scripts/smoke_test_full_pipeline.py` now chains all four services end-to-end against real Discovery/Writing/Verification output for a live check.
- **Impact:** `services/quality-assurance/service.py::run_quality_assurance()` is the pipeline's final stage; its `QualityAssuranceResult` is the terminal artifact PROJECT_NOTES.md's "Final Research Paper Draft" output describes.

## D-014 — Orchestrator and terminal app
- **Date:** 2026-08-27
- **Decision:** Built `orchestrator/pipeline.py::run_pipeline()` as a pure-Python async-generator pipeline runner (no HTTP layer yet) that takes one `ResearchRequest` (`shared/contracts/pipeline_contract.py`) and runs Services 1→2→3→4 in sequence, persisting each stage's structured result under `outputs/<topic-slug>_<run-id>/NN_<stage>/result.json` plus a `final/` folder (draft, quality report, validation report, reference list) and a top-level `metadata.json`. `terminal_app/cli.py` is the current user-facing interface described in PROJECT_NOTES.md — it collects the request (interactively, or from a single command-line argument for quick runs), calls the orchestrator, and prints each progress event plus a final summary.
  - Every service's own progress events (each with a different ad hoc shape — see each `service.py`) are wrapped into one standard format via `_adapt_inner_event()`: `{run_id, stage, service, status, emoji, title, message, details, timestamp}`. This is the explicit "create adapters when formats don't match" rule applied to progress events, not just data contracts.
  - Each of the four services' entry points is a bare `service.py` reached only via `sys.path` insertion (the recurring naming collision first hit in D-010, worked around per-test-file since). The orchestrator is the first place all four get imported into one process, so it loads each one by explicit file path under a unique module name (`_load_service()`) up front, rather than adding a fifth ad hoc workaround.
  - Deliberately built the orchestrator as a plain importable async function first, with no FastAPI/HTTP layer yet — matches the project's explicit working rule ("do not prioritize frontend streaming before the complete pipeline works") and lets the terminal app and a future `POST /research` endpoint both call the same `run_pipeline()` without duplicating pipeline logic.
- **Reason:** This is original integration code specific to this project's four already-adapted services, not something to reuse from an external repository — there is no fifth source repository for "the orchestrator."
- **Alternatives considered:** Writing the FastAPI endpoint first and driving the terminal app through HTTP — rejected for now; an in-process call is simpler and sufficient until a real second consumer (a web frontend) needs the HTTP boundary, and PROJECT_NOTES.md itself frames the terminal app as "the current interface," not the API.
- **Verification:** `tests/orchestrator/test_pipeline.py` fakes all four services (fast, no network/LLM calls) and checks artifact persistence, standardized progress-event shape, and that a stage producing no result raises `PipelineError` rather than silently continuing. `scripts/smoke_test_full_pipeline.py` now calls `run_pipeline()` directly (previously it manually chained the four services) and was re-run live end-to-end successfully.

## D-016 — Full-pipeline live integration test, gated opt-in

Running it unconditionally as part of the suite — rejected per the timing concern above. - **Impact:** Recommended cadence: run this test manually before any Review milestone submission and after any change to `orchestrator/pipeline.py` or any service's public contract (`shared/contracts/*`) — it is the project's real regression net for the full chain, distinct from the fast mocked `tests/orchestrator/test_pipeline.py`/`test_api.py` unit tests that exercise wiring only. Not added to CI/pre-commit given the runtime; this is a documented manual gate, matching the "or documents the manual verification cadence" option from the project's own next-task note.

## D-017 — Asynchronous run API: POST /research/runs, GET /research/runs/{run_id}, SSE events
- **Date:** 2026-08-27
- **Decision:** Added an asynchronous path alongside the existing synchronous `POST /research` (D-015), which is left unchanged for backward compatibility:
  - `POST /research/runs` starts a pipeline run as a background `asyncio` task and returns `{run_id}` immediately (202 Accepted), instead of blocking for the run's full duration.
  - `GET /research/runs/{run_id}` returns the run's current status (`running`/`completed`/`failed`), its `PipelineResult` once completed, or its error message if failed. Returns 404 for an unknown run_id.
  - `GET /research/runs/{run_id}/events` streams every progress event as Server-Sent Events (`text/event-stream`), including events that happened before the client connected (a late subscriber still sees full history, not just what happens from then on), ending with an `event: end` marker. Returns 404 for an unknown run_id.
  - `orchestrator/run_registry.py` is new: an in-memory `dict[run_id, RunState]` with a small pub/sub fan-out (one `asyncio.Queue` per subscriber) so multiple SSE clients could watch the same run simultaneously, though only one is expected in practice for this MVP.
  - `orchestrator/pipeline.py::run_pipeline()` gained an optional `run_id` parameter (defaulting to generating one internally, as before) so the API can generate the run_id up front and return it to the client before the pipeline itself has emitted its first event.
- **Reason:** The project brief explicitly named `GET /research/{run_id}` and progress/event streaming as later additions, deferred at D-015 specifically until the synchronous path was proven — which it now is (D-015's live verification, plus every service chained live through D-016's full-pipeline test). A run can take 15+ minutes on this hardware, so a caller that wants to show live progress (the terminal app already does this in-process; a future web frontend would need it over HTTP) needs a non-blocking start + poll/stream pattern rather than one long-held connection.
- **Alternatives considered:** Replacing `POST /research` outright with the async version — rejected; the synchronous endpoint is already tested and used, and breaking it would be scope creep beyond "add streaming" into "redesign the API." A persistent job queue/database (Celery, Redis, etc.) instead of an in-memory registry — rejected as over-engineering for a single-process local MVP with no multi-worker deployment; the in-memory registry is lost on restart, same limitation the synchronous endpoint already has (a run's live state was never persisted anywhere but the calling process either way — only the on-disk artifacts under `outputs/` survive a restart, for both endpoints equally).
- **Verification:** Unit tests (`tests/orchestrator/test_api.py`) cover: run_id returned immediately, polling to `completed` with the correct result, polling to `failed` with the error message on `PipelineError`, 404 for both GET endpoints on an unknown run_id, and the SSE stream containing the expected progress/result payloads followed by the end marker — all fast, pipeline faked out. Also manually verified against a real running `uvicorn` server: `POST /research/runs` against a real request returned a run_id immediately, `GET /research/runs/{run_id}` showed `status: "running"`, and the SSE endpoint streamed real live progress events from an actual in-progress Discovery stage.
- **Bug found and fixed during this manual verification:** the Research Discovery Service's own progress-event text included a leftover string from its original source repo — `"Generating search queries with Claude…"` — inaccurate for this project, which only ever calls the local Ollama model (`qwen3.5:9b`), never Claude or any cloud model. This had been emitting silently all along (the terminal app already prints every event's `message` field) but was only actually read closely once the SSE stream's raw payload was inspected here. Fixed to `"Generating search queries with the local model…"`; two similar leftover code comments (one referencing "Claude", one referencing an unused "scite" integration from the source repo) were also cleaned up in the same file. This is a plain accuracy bug fix, unrelated to D-004's documentation-privacy rule — D-004 governs what project-facing *docs* say about component provenance, not runtime-user-facing text describing which model is actually running.
- **Impact:** `orchestrator/api.py` now exposes both the original synchronous endpoint and the new asynchronous/streaming trio; `orchestrator/run_registry.py` is the new supporting module. This completes the two explicitly-deferred API items from the project brief — no further API work is planned for this MVP.
